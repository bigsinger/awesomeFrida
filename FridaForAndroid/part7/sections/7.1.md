# 7.1 ELF文件结构解析

> 核心要点：理解 ELF 文件格式是逆向 Android SO 文件的基础。本节将从 ELF header 开始，逐层解析 section headers、program headers 以及关键段的含义。

## 1. ELF 文件概述

ELF（Executable and Linkable Format）是 Linux 和 Android 系统中可执行文件与共享库（SO）的标准文件格式。一个典型的 ELF 文件由以下部分组成：

```
┌─────────────────────────────┐
│      ELF Header (52/64B)    │  ← 文件头，描述整体结构
├─────────────────────────────┤
│    Program Headers (PHDR)   │  ← 程序头，描述段（Segment），运行时使用
├─────────────────────────────┤
│                             │
│   Section / Segment Data    │  ← 实际的代码、数据、符号表等内容
│                             │
├─────────────────────────────┤
│    Section Headers (SHDR)   │  ← 节头表，描述节（Section），链接时使用
└─────────────────────────────┘
```

### 1.1 ELF Header

ELF header 位于文件开头，使用 `readelf -h` 可以查看：

```bash
# 查看 SO 文件的 ELF header
readelf -h libnative-lib.so

# 输出示例：
ELF Header:
  Magic:   7f 45 4c 46...  # ELF magic: \x7fELF
  Class:                    ELF64        # 32位(ELF32)或64位(ELF64)
  Data:                     2's complement, little endian  # 小端字节序
  Version:                  1 (current)
  OS/ABI:                   UNIX - System V
  ABI Version:              0
  Type:                     DYN (Shared object file)  # 共享库类型
  Machine:                  AArch64       # ARM 64位架构
  Entry point address:      0x0           # 入口地址（SO通常为0）
  Start of program headers: 64 (bytes into file)
  Start of section headers: 13592 (bytes into file)
  Flags:                    0x0
  Size of this header:      64 (bytes)
  Size of program headers:  56 (bytes)
  Number of program headers: 9
  Size of section headers:  64 (bytes)
  Number of section headers: 25
  Section header string table index: 24
```

**关键字段说明：**

| 字段 | 含义 |
|------|------|
| `e_type` | 文件类型：ET_REL(1) 可重定位、ET_EXEC(2) 可执行、ET_DYN(3) 共享库 |
| `e_machine` | 目标架构：EM_ARM(40)、EM_AARCH64(183)、EM_X86_64(62) |
| `e_phoff` | Program header table 的文件偏移 |
| `e_shoff` | Section header table 的文件偏移 |
| `e_phnum` | Program header 的数量 |
| `e_shnum` | Section header 的数量 |
| `e_shstrndx` | 节头字符串表所在的 section 索引 |

### 1.2 Section Headers（节头）

Section 是 ELF 文件的逻辑组成单元，链接器（linker）在编译链接阶段使用 section 来组织代码和数据。使用 `readelf -S` 查看：

```bash
# 查看 SO 文件的 section headers
readelf -S libnative-lib.so

# 输出示例（核心section）：
Section Headers:
  [Nr] Name              Type            Address          Off    Size   ES Flg Lk Inf Al
  [ 0]                   NULL            0000000000000000 000000 000000 00      0   0  0
  [ 5] .dynsym           DYNSYM          0000000000000328 000328 0001c8 18      A  6   1
  [ 6] .dynstr           STRTAB          00000000000004f0 0004f0 0000b0 00      A  0   0
  [ 7] .hash             HASH            00000000000005a0 0005a0 000014 04      A  5   0
  [ 9] .rela.dyn         RELA            00000000000005c8 0005c8 000018 18      A  5   0
  [11] .text             PROGBITS        00000000000005f0 0005f0 000270 00     AX  0   0
  [13] .rodata           PROGBITS        0000000000000860 000860 000030 00      A  0   0
  [15] .data.rel.ro      PROGBITS        00000000000018d8 0008d8 000010 00     WA  0   0
  [17] .bss              NOBITS          00000000000018f0 0008e8 000008 00     WA  0   0
  [19] .init_array       INIT_ARRAY      00000000000018e8 0008e8 000008 08     WA  0   0
```

**常见 Section 类型及用途：**

| Section | 用途 | 是否必须 |
|---------|------|---------|
| `.text` | 可执行代码段（机器指令） | ✅ |
| `.rodata` | 只读数据（字符串常量等） | ✅ |
| `.data` | 已初始化的全局/静态变量 | ❌ |
| `.bss` | 未初始化的全局/静态变量 | ❌ |
| `.dynsym` | 动态符号表（导出的函数和全局变量） | ✅ |
| `.dynstr` | 动态符号表中符号名称的字符串表 | ✅ |
| `.hash` | 符号哈希表（加速符号查找） | ✅ |
| `.rel.dyn` / `.rela.dyn` | 动态重定位表 | ✅ |
| `.plt` | 过程链接表（延迟绑定） | ❌ |
| `.got` / `.got.plt` | 全局偏移表 | ✅ |
| `.init_array` | 构造函数数组（SO加载时自动执行） | ❌ |
| `.fini_array` | 析构函数数组（SO卸载时自动执行） | ❌ |
| `.comment` | 编译器版本信息 | ❌ |
| `.note.gnu.build-id` | 构建ID（用于调试符号匹配） | ❌ |

### 1.3 Program Headers（程序头）

Program header 描述的是运行时段的布局（Segment），由 loader（linker）在加载 SO 时使用。使用 `readelf -l` 查看：

```bash
# 查看 SO 文件的 program headers
readelf -l libnative-lib.so

# 输出示例：
Program Headers:
  Type           Offset   VirtAddr          PhysAddr          FileSiz  MemSiz   Flg Align
  PHDR           0x000040 0x0000000000000040 0x0000000000000040 0x0001f8 0x0001f8 R   0x8
  LOAD           0x000000 0x0000000000000000 0x0000000000000000 0x000890 0x000890 R   0x1000
  LOAD           0x0008e8 0x00000000000018e8 0x00000000000018e8 0x000008 0x000018 RW  0x1000
  DYNAMIC        0x0008a0 0x00000000000008a0 0x00000000000008a0 0x000130 0x000130 RW  0x8
  GNU_STACK      0x000000 0x0000000000000000 0x0000000000000000 0x000000 0x000000 RW  0x10
  GNU_RELRO      0x0008e8 0x00000000000018e8 0x00000000000018e8 0x000018 0x000018 R   0x1
```

**关键 Program Header 类型：**

| Type | 含义 |
|------|------|
| `PT_LOAD` (1) | 可加载段，linker 将其映射到内存 |
| `PT_DYNAMIC` (2) | 动态链接信息段 |
| `PT_INTERP` (3) | 解释器路径（可执行文件用） |
| `PT_GNU_STACK` | 栈可执行性标志 |
| `PT_GNU_RELRO` | 只读重定位（RELRO 安全机制） |

> **注意**：Section 和 Segment 是 ELF 文件的两种不同视角。Section 是"链接视角"，Segment 是"运行视角"。同一个数据区域可以同时属于一个 Section 和一个 Segment。

## 2. 动态符号表 (.dynsym)

`.dynsym` 是 SO 文件中最重要的段之一，它列出了所有导出的动态符号（函数和全局变量）。这些符号可以通过 `dlsym` 在运行时查找。

使用 `readelf -s` 查看动态符号表：

```bash
# 查看动态符号表
readelf -s libnative-lib.so

Symbol table '.dynsym' contains 19 entries:
   Num:    Value          Size Type    Bind   Vis      Ndx Name
     0: 0000000000000000     0 NOTYPE  LOCAL  DEFAULT  UND 
     1: 00000000000005f0   112 FUNC    GLOBAL DEFAULT   11 Java_com_roysue_r0so_MainActivity_stringFromJNI
     2: 0000000000000660   100 FUNC    GLOBAL DEFAULT   11 Java_com_roysue_r0so_MainActivity_stringFromJNI2
     3: 00000000000006c4    84 FUNC    GLOBAL DEFAULT   11 stringFromJNI3
     4: 0000000000000718    40 FUNC    GLOBAL DEFAULT   11 JNI_OnLoad
     5: 0000000000000000     0 FUNC    GLOBAL DEFAULT  UND __android_log_print
```

### 2.1 符号绑定属性（Bind）

| 属性 | 说明 |
|------|------|
| `LOCAL` | 局部符号，仅对当前 SO 可见，外部不可访问 |
| `GLOBAL` | 全局符号，可被其他 SO 引用 |
| `WEAK` | 弱符号，可以被同名的 GLOBAL 符号覆盖 |

### 2.2 符号类型（Type）

| 类型 | 说明 |
|------|------|
| `FUNC` | 函数 |
| `OBJECT` | 全局变量或对象 |
| `NOTYPE` | 无类型（通常用于未定义符号） |
| `TLS` | 线程局部存储 |

### 2.3 实时查看导出函数

使用 Frida 可以实时查看加载后 SO 的导出函数地址：

```javascript
// 查看 libnative-lib.so 的所有导出函数
var module = Process.findModuleByName("libnative-lib.so");
var exports = module.enumerateExports();
exports.forEach(function(exp) {
    if (exp.type === "function") {
        console.log(exp.name + " @ " + exp.address + 
                    " (offset: 0x" + exp.address.sub(module.base).toString(16) + ")");
    }
});
```

运行输出示例：

```
Java_com_roysue_r0so_MainActivity_stringFromJNI @ 0x7bcf05f0 (offset: 0x5f0)
Java_com_roysue_r0so_MainActivity_stringFromJNI2 @ 0x7bcf0660 (offset: 0x660)
stringFromJNI3 @ 0x7bcf06c4 (offset: 0x6c4)
JNI_OnLoad @ 0x7bcf0718 (offset: 0x718)
```

## 3. .init_array 与 .fini_array

### 3.1 .init_array

`.init_array` 是一个函数指针数组，其中的每个函数指针在 SO 被 `dlopen` 加载后、`JNI_OnLoad` 调用之前自动执行。Android linker 在 `call_constructors` 函数中按顺序调用这些函数。

```cpp
// native-lib.cpp 中的构造函数示例
// 不属于 native-lib.cpp，展示.init_array的典型用法

// __attribute__((constructor)) 会将函数注册到 .init_array
__attribute__((constructor))
void my_init() {
    __android_log_print(ANDROID_LOG_INFO, "r0so", "init function called!");
    // 反调试：创建监控线程
    // 加固：解密 .dex 或 .text 段
}

__attribute__((destructor)) 
void my_fini() {
    __android_log_print(ANDROID_LOG_INFO, "r0so", "fini function called!");
}
```

编译后查看 `.init_array`：

```bash
# 查看 .init_array 的内容
readelf -x .init_array libnative-lib.so

# 或通过 readelf -S 确认其存在
readelf -S libnative-lib.so | grep init_array
```

`.init_array` 是 **反调试和加固** 的重要载体。很多加固方案的检测线程、内存解密逻辑都在这里启动。

### 3.2 .init_array vs JNI_OnLoad 执行顺序

```
dlopen("/data/app/xxx.so")
    ↓
linker 加载 .text/.data 等段进内存
    ↓
linker 执行重定位（.rela.dyn）
    ↓
linker 调用 call_constructors()   ← 在这里执行 .init_array
    ↓
依次调用 .init_array[0], .init_array[1], ...
    ↓
（可选）调用 init_func（.init 段）
    ↓
返回 dlopen 结果
    ↓
Java VM 调用 JNI_OnLoad()        ← 在这里动态注册 JNI 函数
```

> **关键洞察**：由于 `.init_array` 在 `JNI_OnLoad` 之前执行，这意味着有些反调试线程在 JNI 函数被 Hook 之前就已经启动。这也是为什么在 Part9 中我们需要 Hook `call_constructors` 来拦截 `.init_array`。

## 4. 动态段 (DT_* 条目)

使用 `readelf -d` 查看动态段：

```bash
readelf -d libnative-lib.so

Dynamic section at offset 0x8a0 contains 16 entries:
  Tag        Type                         Name/Value
  0x00000005 (STRTAB)                     0x4f0
  0x00000006 (SYMTAB)                     0x328
  0x0000000a (STRSZ)                      176 (bytes)
  0x0000000b (SYMENT)                     24 (bytes)
  0x00000003 (PLTGOT)                     0x18c0
  0x00000017 (JMPREL)                     0x5e0
  0x00000002 (PLTRELSZ)                   8 (bytes)
  0x00000019 (INIT_ARRAY)                 0x18e8
  0x0000001b (INIT_ARRAYSZ)               8 (bytes)
  0x0000001a (FINI_ARRAY)                 0x18f0
  0x0000001c (FINI_ARRAYSZ)               8 (bytes)
  0x00000001 (NEEDED)                     liblog.so

  0x00000001 (NEEDED)                     libm.so
  0x0000001e (FLAGS)                     BIND_NOW
```

**关键 DT_* 条目说明：**

| Tag | 含义 |
|-----|------|
| `DT_SYMTAB` / `DT_STRTAB` | 动态符号表与字符串表地址 |
| `DT_INIT_ARRAY` / `DT_INIT_ARRAYSZ` | init_array 的地址和大小 |
| `DT_NEEDED` | 依赖的其他 SO（如 liblog.so） |
| `DT_PLTGOT` | GOT（全局偏移表）地址 |
| `DT_JMPREL` | PLT 重定位表 |
| `DT_FLAGS` / `DT_BIND_NOW` | 绑定策略标志 |

## 5. 通过 Frida 读取 ELF Header

除了使用 `readelf` 命令行工具，我们还可以在 Frida 脚本中实时读取 ELF header 信息：

```javascript
// 实时读取 ELF header
function dump_elf_header(moduleName) {
    var mod = Process.findModuleByName(moduleName);
    if (!mod) {
        console.log("Module not found: " + moduleName);
        return;
    }
    
    var base = mod.base;
    console.log("[*] Module: " + mod.name + " @ " + base);
    
    // ELF Header 关键字段
    var magic = base.readCString(4);
    var class_byte = base.add(4).readU8();      // 1=32bit, 2=64bit
    var endian = base.add(5).readU8();           // 1=little, 2=big
    var e_type = base.add(16).readU16();         // 2=DYN(SO)
    var e_machine = base.add(18).readU16();      // 0x28=ARM, 0xB7=AArch64
    var e_phoff = base.add(class_byte === 2 ? 32 : 28).readU32(); // program header offset
    var e_shoff = base.add(class_byte === 2 ? 40 : 32).readU32(); // section header offset
    var e_phnum = base.add(class_byte === 2 ? 54 : 44).readU16(); // program header count
    var e_shnum = base.add(class_byte === 2 ? 60 : 50).readU16(); // section header count
    
    console.log("[*] ELF Magic: " + magic);
    console.log("[*] Class: " + (class_byte === 2 ? "ELF64" : "ELF32"));
    console.log("[*] Endian: " + (endian === 1 ? "Little" : "Big"));
    console.log("[*] Type: " + (e_type === 3 ? "DYN (SO)" : "0x" + e_type.toString(16)));
    console.log("[*] Machine: " + (e_machine === 0xB7 ? "AArch64" : "0x" + e_machine.toString(16)));
    console.log("[*] Program headers: " + e_phnum + " @ 0x" + e_phoff.toString(16));
    console.log("[*] Section headers: " + e_shnum + " @ 0x" + e_shoff.toString(16));
}

// 使用
dump_elf_header("libnative-lib.so");
```

## 6. 引用代码分析：native-lib.cpp 第1-47行

从 `native-lib.cpp` 的源代码可以看出 JNI 函数的导出机制：

```cpp
// 引用：Chap11/r0so/app/src/main/cpp/native-lib.cpp 第1-47行
// 静态注册：函数名遵循 Java_com_xxx 规则
extern "C" JNIEXPORT jstring JNICALL
Java_com_roysue_r0so_MainActivity_stringFromJNI(
        JNIEnv* env,
        jobject /* this */) {                    // 第17-22行
    std::string hello = "Hello from C++ r0ysue";
    return env->NewStringUTF(hello.c_str());
}

extern "C" JNIEXPORT jstring JNICALL
Java_com_roysue_r0so_MainActivity_stringFromJNI2(
        JNIEnv* env,
        jobject /* this */) {                    // 第25-31行
    std::string hello = "Hello from C++ stringFromJNI2 r0ysue ";
    return env->NewStringUTF(hello.c_str());
}

// 非标准命名（无 Java 包名前缀），用于动态注册
JNIEXPORT jstring JNICALL stringFromJNI3(
        JNIEnv* env,
        jobject /*this*/) {                      // 第41-46行
    std::string hello = "Hello from C++ stringFromJNI3 r0ysue ";
    return env->NewStringUTF(hello.c_str());

```

编译后，通过 `readelf -s` 可以看到前两个函数进入 `.dynsym` 表成为**导出符号**，而 `stringFromJNI3` 由于没有 `extern "C"` 且函数名不包含 Java 包名路径，其导出方式取决于编译器和链接脚本。在本例中由于在 `JNI_OnLoad` 中通过 `RegisterNatives` 注册，它不需要作为符号被外部可见。

### 练习2：Frida 脚本——枚举 Section 信息

```javascript
// 高级：使用 Frida 的 Module API 枚举 section 信息
// Frida 的 NativeFunction 可以调用 linker 内部的函数来获取 section 信息
// 也可通过内存扫描 ELF section header table 的方式

function enumerateSections(moduleName) {
    var mod = Process.findModuleByName(moduleName);
    if (!mod) return;
    
    var base = mod.base;
    var class_byte = base.add(4).readU8();
    var is64 = class_byte === 2;
    
    // 解析 ELF header 获取 section header table 位置
    var e_shoff = is64 ? base.add(40).readU64() : base.add(32).readU32();
    var e_shentsize = is64 ? base.add(58).readU16() : base.add(46).readU16();
    var e_shnum = is64 ? base.add(60).readU16() : base.add(48).readU16();
    var e_shstrndx = is64 ? base.add(62).readU16() : base.add(50).readU16();
    
    // 读取 section name string table
    var shstrtab_offset = e_shstrndx * e_shentsize;
    var shstrtab_sec = base.add(e_shoff + shstrtab_offset);
    var shstrtab_addr = is64 ? 
        base.add(shstrtab_sec.add(24).readU64()) : 
        base.add(shstrtab_sec.add(16).readU32());
    
    console.log("[*] Sections in " + moduleName + ":");
    for (var i = 0; i < e_shnum; i++) {
        var shdr = base.add(e_shoff + i * e_shentsize);
        var sh_name = is64 ? shdr.readU32() : shdr.readU32();
        var sh_addr = is64 ? shdr.add(16).readU64() : shdr.add(12).readU32();
        var sh_size = is64 ? shdr.add(32).readU64() : shdr.add(20).readU32();
        var name = shstrtab_addr.add(sh_name).readCString();
        
        if (sh_addr > 0) {
            console.log("  " + name + " @ 0x" + sh_addr.toString(16) + 
                       " size: 0x" + sh_size.toString(16));
        }
    }
}

enumerateSections("libnative-lib.so");
```

## 总结

- ELF 文件由 **ELF Header** → **Program Headers** → **Data** → **Section Headers** 组成
- **Section 是链接视角**，**Segment 是运行视角**，两者描述同一数据的不同角度
- `.dynsym` 动态符号表包含了可以被外部引用的函数和全局变量
- `.init_array` 是 SO 初始化函数数组，在 `dlopen` 返回前、`JNI_OnLoad` 前执行
- Frida 的 `Process.findModuleByName()` + `module.enumerateExports()` 可以实时查看导出符号
- 理解 ELF 结构是分析 SO 加固、反调试机制的前提
